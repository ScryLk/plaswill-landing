# Prompt para continuar na VPS

Copie o texto abaixo para o agente que tem acesso à VPS. Não inclua chaves no prompt.

---

Quero conectar as métricas PostHog da landing Plaswill ao sistema existente em **https://indicadores.plaswill.tech**. O Indicators não está no GitHub: localize seu código e processo oficial de versionamento na VPS. A landing está em https://site.plaswill.tech, repositório https://github.com/ScryLk/plaswill-landing. A preparação está na branch **feat/posthog-landing-analytics**; leia POSTHOG.md, PROMPT-VPS-INDICATORS.md e o diff antes de trabalhar. Não faça merge automático.

Comece com auditoria somente de leitura. O README da landing documenta a VPS 179.199.151.3/srv2045098, back-office em /opt/plaswill e landing separada em /opt/plaswill-site; confirme tudo no host. Verifique instruções locais, alterações não commitadas e commit implantado. Inspecione serviços Docker, mounts, código Indicators, stack real, autenticação/autorização (inclusive eventual Nextcloud), conectores, dashboards/gráficos, TV/playlists, scheduler/cache, testes, backups e restauração. Não imprima ambientes de containers, arquivos .env, tokens, eventos individuais ou dumps contendo dados pessoais. Não presuma stack nem que Redis/MariaDB pertencem ao Indicators. Não altere a VPS durante essa auditoria.

Prepare uma cópia de desenvolvimento recuperável do Indicators fora dos diretórios de produção, conforme o processo existente. Preserve código e metadados atuais; não crie repositório remoto nem infraestrutura pesada sem necessidade. Registre mudanças revisáveis, testes e rollback. Não edite produção diretamente.

Para obter a preparação da landing: use Git HTTPS já configurado, faça fetch da branch e examine o diff em uma cópia de desenvolvimento. Não use reset --hard/stash destrutivo nem substitua configurações locais. Se a branch não estiver publicada ou ainda não tiver sido revisada/integrada ao branch aprovado de implantação, informe isso e homologue a cópia; **não dê git pull em main esperando alterações ainda não integradas**. Depois de revisão e autorização explícita para produção, o fluxo documentado é `cd /opt/plaswill-site && git pull --ff-only`, seguido de `cd deploy && docker compose up -d --build site`. Confirme antes qual branch foi aprovada e se o checkout está limpo. Não faça merge automaticamente.

Na landing, use o Compose já preparado e configure deploy/.env preservando os valores existentes. POSTHOG_ENABLED=false por padrão; token público POSTHOG_PROJECT_TOKEN (phc_), POSTHOG_INGESTION_HOST regional us.i.posthog.com ou eu.i.posthog.com, POSTHOG_SITE_HOST=site.plaswill.tech e POSTHOG_ENVIRONMENT=production. Em homologação use projeto e host separados e environment=staging. Nunca coloque POSTHOG_PERSONAL_API_KEY na landing. A configuração é de runtime; recriar somente o serviço site reaplica os envs. Não mexa no Caddy, Nextcloud, bancos ou Compose compartilhado para essa alteração. Revise política de privacidade, região, retenção e transferência internacional antes da ativação.

O SDK já possui consentimento prévio, recusa/revogação, captura explícita e allowlist que exclui campos e mensagens. Não ative autocapture, replay, heatmaps ou perfis pessoais. Leia o contrato schema_version=1 em POSTHOG.md; confirme os eventos reais de homologação: $pageview, product_details_opened, sample_request_started, quote_cta_clicked, whatsapp_click, phone_click, email_click, quote_form_started, quote_validation_attempted (valid boolean) e quote_whatsapp_open_attempted. Propriedades de filtro: site_host, environment, schema_version, page_path, product_id/category, section e UTMs sanitizadas. Eventos do formulário não comprovam envio/recebimento; cliques não comprovam conversa ou venda.

Implemente o conector no BACKEND REAL do Indicators usando a API oficial `POST /api/projects/{project_id}/query/`, HogQL predefinido e parâmetros validados. Verifique documentação atual, região/host da Query API (diferente do host de ingestão), escopo mínimo e acesso ao projeto. Configure a personal API key somente pelo mecanismo seguro do servidor, restrita ao projeto/consulta quando possível. Não envie segredos ao navegador ou logs. Nunca execute SQL arbitrário vindo do frontend/IA.

MVP: visitantes estimados distintos, pageviews, sessões não vazias, aquisição por sessão, fichas/produtos mais consultados, amostras iniciadas, cliques comerciais e tentativas de orçamento separadas. Defina cada unidade/fórmula e funil temporal por sessão/produto. Filtre sempre domínio, ambiente, schema e período UTC semiaberto; calendário America/Sao_Paulo. Hoje/ontem/7/30/90 dias e personalizado limitado a 90 dias, máximo inicial de 100 linhas, top 10 produtos. Não some distintos diários nem misture eventos, sessões e visitantes na taxa. Não invente receita/vendas.

Reutilize cache/scheduler existentes com atualização de 30 minutos, timeout, concorrência limitada, backoff e Retry-After/429. Preserve último resultado válido e exiba data/stale. Não consulte PostHog por renderização. Integre rotas internas à autenticação/autorização corporativa, com validação e rate limit. Nunca crie rotas públicas de métricas comerciais. Diferencie não configurado, vazio confirmado, erro, válido e stale; não substitua falta de dados por zero.

Adicione “Landing — Desempenho Comercial” à interface e playlists existentes: quatro KPIs, aquisição por sessões, top produtos, funil e metadados. Respeite desktop/tablet/mobile e modo TV sem rolagem vertical, sem mudar a alternância existente. A IA usa somente operações aprovadas sobre agregados com fonte/período/atualização/definição. Não exporte eventos brutos, IDs de visitantes, PII ou gravações para o Indicators.

Teste o código da landing com build, typecheck, scripts/verificar-cabecalho.mjs, scripts/test-analytics.mjs e scripts/test-analytics-browser.mjs (este último intercepta o PostHog e não valida entrega real). Execute também os testes existentes do Indicators e novos casos de autenticação, respostas válidas/vazias/malformadas, filtros, funis, 401/403/429/5xx, timeout, cache/stale, ausência de PII/segredos e isolamento entre ambientes.

Homologue o fluxo real em projeto separado: evento sintético autorizado na landing → chegada ao PostHog correto → Query API → agregado validado sem duplicação → cache → dashboard Indicators. Não ative jobs ou gere eventos sintéticos em produção. Se faltar credencial, consentimento ou eventos, use fixtures apenas em testes, documente a pendência e não declare integração real concluída.

Entregue diagnóstico, alterações revisáveis, catálogo/query templates, variáveis sem valores secretos, testes com resultados distintos entre simulados e reais, instruções de publicação e rollback. Pause para aprovação antes de alterar produção. Rollback inicial: desligar POSTHOG_ENABLED e recriar apenas site, recarregar abas antigas; desligar somente o conector/job novo no Indicators. Não faça merge, deploy ou mudanças em serviços compartilhados automaticamente.
